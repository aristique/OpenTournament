# Требования лабораторной №2

Источник: приложенная пользователем методичка «Лабораторная работа №2. Микросервисное приложение», прочитана полностью 2026-11-13. Ниже — разбор требований учебного задания; исходный приложенный файл не публикуется.

## Обязательно

| Требование | Как подтвердить при защите |
| --- | --- |
| Минимум «5–6» backend-микросервисов (формулировка задания) | Для проекта пользователь запросил шесть; показать шесть отдельных бизнес-сервисов |
| У каждого своя ответственность, API и бизнес-логика | Показать границы и отдельные операции каждого сервиса |
| Независимый запуск и отдельная конфигурация | Запустить сервис отдельно с его настройками; независимый запуск не гарантирует успешность операций, которым нужен недоступный сосед |
| REST/gRPC API и взаимодействие сервисов | Показать запросы и сквозной сценарий; оба протокола одновременно не требуются |
| База данных и логическое разделение сервисов | Показать сохранение и чтение данных; общая БД допускается только с архитектурным обоснованием |
| Authentication/authorization | Показать проверку личности пользователя и его прав на действие |
| Обработка ошибок в каждом сервисе | Проверить неверный ввод, отсутствие ресурса, ошибки доступа, внешних сервисов, тайм-ауты и ошибки БД |
| Logging в каждом сервисе | В записях есть время, сервис, уровень, Request ID и сообщение |
| Configuration management | Показать отделённые от кода настройки сервисов |
| Документация API | Документировать API; основные адреса запросов привести в README |
| Health check endpoints | Показать запросы проверки работоспособности; конкретные имена /health и /ready приведены как примеры |
| Обоснование выбора технологий | Объяснить, какую задачу решает каждая технология и почему подходит проекту |

База данных, UI, API Gateway и reverse proxy **не засчитываются** как бизнес-микросервисы. Набор из frontend, одного backend и БД недостаточен.

## Рекомендации, а не отдельные обязательные требования

- Отдельная БД у каждого сервиса. Общая допустима с обоснованием; прямой доступ к чужим данным увеличивает связанность.
- Хотя бы один сценарий асинхронного взаимодействия. Отдельный брокер не указан как обязательный.
- API Gateway; перечисленные routing/auth/rate limiting/aggregation/logging — возможные функции, не обязательный набор.
- OpenAPI и Swagger UI для REST. Документация обязательна, конкретный инструмент рекомендован.
- Структурированные логи, например JSON. Перечисленные поля обязательны независимо от формата.
- Не возвращать пользователю stack trace — рекомендация формулировки методички; проекту разумно принять её как правило.

## Примеры, которые не фиксируют проект

Предметная область свободная. Интернет-магазин, названия сервисов, язык, фреймворк, СУБД и брокер приведены как варианты. Дерево каталогов с docker-compose.yml — пример структуры: обязательность Docker, Compose и именно таких путей отдельно не установлена. Frontend, облако, Kubernetes, реальные денежные платежи и доставка не требуются текстом задания.

## Критерии оценки

| Критерий | Вес |
| --- | --- |
| 5–6+ микросервисов | 20% |
| Архитектура и разделение ответственности | 20% |
| Взаимодействие сервисов | 15% |
| Database / persistence | 10% |
| API и документация | 10% |
| Authentication / authorization | 5% |
| Logging / error handling | 10% |
| Тестирование | 10% |

Тестирование вынесено в критерии оценки, хотя не повторено в списке раздела 9. Поэтому для цели полноценной сдачи включаем его в проект. Объём тестов согласуем по важным сценариям, а не по искусственному проценту покрытия.
