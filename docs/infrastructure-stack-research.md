# Инфраструктура локального прототипа: сравнение кандидатов

Дата исследования: **2026-11-13**. Это материал для выбора, а не утверждённое решение.
Контекст из задания: новичок, неделя по несколько часов в день, шесть backend-сервисов; Docker с Linux-контейнерами уже работает, RAM 31 GiB, Docker доступно около 15 GiB; образ PostgreSQL 17.9 есть, RabbitMQ ещё нет.
Отдельно подтверждено в основном исследовании окружения: Docker `hello-world` успешно запущен из имеющегося образа, локальный Python HTTP-запрос успешно выполнен после разрешения доступа.
Это подтверждает базовую работоспособность окружения; PostgreSQL, RabbitMQ и весь прикладной стек пока не проверялись запуском.

Цель: постоянные данные, API, авторизация, понятные ошибки и логи, тесты и хотя бы один осмысленный асинхронный сценарий.
Оценки удобства и сложности ниже — инженерные выводы применительно к этому сроку; это не результаты измерений производительности.

## Три разные задачи

- **Постоянное хранилище** отвечает «каково текущее состояние?»: пользователи, бронирования, результаты. Транзакция PostgreSQL объединяет изменения в операцию «всё или ничего». [PostgreSQL: transactions](https://www.postgresql.org/docs/17/tutorial-transactions.html)
- **Очередь** передаёт работу другому сервису: «обработай событие, когда сможешь». RabbitMQ хранит сообщения в очередях и передаёт потребителям; долговечность очереди и сообщения настраиваются отдельно. [RabbitMQ: queues](https://www.rabbitmq.com/docs/queues)
- **Кеш** в предлагаемой архитектуре был бы восстанавливаемой копией результата ради повторного чтения. Redis также умеет постоянное хранение, поэтому название продукта само по себе не определяет его роль. [Redis: persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

Вывод для прототипа: сначала база и один механизм доставки событий; отдельный кеш добавлять только после появления конкретной проблемы. Очередь не заменяет таблицы предметной области, а сохранение таблиц само по себе не гарантирует доставку события.

## Постоянные данные

| Кандидат | Что подтверждают документы | Применимость к этой неделе — вывод |
|---|---|---|
| PostgreSQL | Транзакции; ограничения UNIQUE, CHECK, FK; несколько отдельных БД в одном серверном кластере. [Транзакции](https://www.postgresql.org/docs/17/tutorial-transactions.html), [ограничения](https://www.postgresql.org/docs/17/ddl-constraints.html), [БД](https://www.postgresql.org/docs/17/manage-ag-overview.html) | Основной кандидат: один знакомый SQL-подход для всех сервисов, образ уже есть; нет необходимости изучать разные СУБД одновременно. |
| SQLite | Встраиваемое локальное хранилище без отдельного серверного администрирования; одновременно пишет один writer на файл БД. [SQLite: appropriate uses](https://www.sqlite.org/whentouse.html) | Отличный способ сократить инфраструктуру: отдельный файл каждого сервиса. Подходит при небольшом числе записей; слабее демонстрирует управление серверными пользователями и конкурентными подключениями. |
| MySQL / InnoDB | Транзакции с commit/rollback/crash recovery, блокировки строк. [MySQL: InnoDB](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html) | Полноценная SQL-альтернатива, особенно если уже знакома. В данном контексте явного выигрыша перед имеющимся PostgreSQL не выявлено. |
| MongoDB | Документы одной коллекции могут иметь разные поля; модель строится по способу чтения данных; schema validation доступна. [MongoDB: data modeling](https://www.mongodb.com/docs/manual/data-modeling/) | Рассмотреть для естественно документной области. Гибкая структура не освобождает от проектирования данных; добавлять ради разнообразия за неделю невыгодно. |

SQLite не является «игрушечной базой»: официальная документация прямо описывает другое назначение — локальное хранение приложения вместо общего сетевого SQL-сервера. Для шести независимых локальных процессов это допустимый компромисс. [SQLite: appropriate uses](https://www.sqlite.org/whentouse.html)
Предварительный shortlist: PostgreSQL; SQLite — запасной вариант, если инфраструктура начинает съедать время разработки. MongoDB и MySQL остаются альтернативами при предметной причине или прежнем опыте.

## Один PostgreSQL или шесть

В терминологии PostgreSQL один server cluster содержит несколько БД; роли общие для кластера, соединение выбирает одну БД. Здесь «один сервер» означает один экземпляр PostgreSQL, а не кластер высокой доступности. [PostgreSQL: database overview](https://www.postgresql.org/docs/17/manage-ag-overview.html)

| Вариант | Границы данных | Отказы и обслуживание — вывод |
|---|---|---|
| Одна общая БД, общие таблицы | Сервисы могут получить прямую зависимость от чужих таблиц; раздельные схемы и права дают более явные границы. [PostgreSQL: overview](https://www.postgresql.org/docs/17/manage-ag-overview.html) | Самый короткий старт, но сложнее показывать самостоятельное владение данными; общая миграция легче затрагивает соседей. |
| Один экземпляр, шесть БД и шесть login-ролей | Отдельная БД каждому сервису, собственные миграции и учётная запись; роли и разрешения всё равно требуют настройки. [PostgreSQL: overview](https://www.postgresql.org/docs/17/manage-ag-overview.html), [role attributes](https://www.postgresql.org/docs/17/role-attributes.html) | Хороший компромисс: один процесс и каталог данных, но логические границы. Остановка сервера затрагивает все шесть; CPU, RAM и диск общие. |
| Шесть экземпляров, отдельные volumes и роли | Отдельная конфигурация каждого PostgreSQL. | Больше конфигураций, подключений и резервных копий. Ошибка/перезапуск одного процесса локальнее, но общий Docker-хост и диск остаются общей точкой отказа. |

Вторая строка — сильный кандидат для обучения: **шесть БД, а не просто шесть пользователей в одной общей БД**. Сервис должен обращаться к чужой логике через API/события — предлагаемое архитектурное правило, а не встроенный запрет SQL.
Нельзя считать, что шесть пользователей автоматически закрывают остальные БД: PostgreSQL по умолчанию выдаёт `PUBLIC` права `CONNECT` и `TEMPORARY` на базы. [PostgreSQL: privileges](https://www.postgresql.org/docs/17/ddl-priv.html)
Предлагаемая настройка: отозвать эти общие права для каждой прикладной БД и выдать своей роли нужные права; отдельно проверить таблицы, схемы и членство ролей. Возможность подключиться и право читать таблицу — разные разрешения. [PostgreSQL: privileges](https://www.postgresql.org/docs/17/ddl-priv.html)
Приложениям не выдавать superuser: эта роль обходит проверки прав. Аутентификацию подключений задаёт `pg_hba.conf`; это дополнительный уровень к SQL-разрешениям. [Role attributes](https://www.postgresql.org/docs/17/role-attributes.html), [pg_hba.conf](https://www.postgresql.org/docs/17/auth-pg-hba-conf.html)

## Передача работы между сервисами

| Кандидат | Модель и надёжность по документации | Цена выбора на этой неделе — вывод |
|---|---|---|
| HTTP-only | HTTP задаёт запросы, ответы и семантику методов; протокол не является постоянной очередью заданий. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) | Наименьше инфраструктуры для синхронных сценариев. Для переживания недоступности получателя понадобятся собственное хранение работы и повторы; учебный брокерный сценарий не показывает. |
| RabbitMQ | Очереди, exchanges, publisher confirms и consumer acknowledgements; при сбоях возможны повторные доставки. [Queues](https://www.rabbitmq.com/docs/queues), [confirms](https://www.rabbitmq.com/docs/confirms), [reliability](https://www.rabbitmq.com/docs/reliability) | Основной кандидат для фоновой задачи или события: явная модель «сообщение → обработка → подтверждение». Нужно разобраться с маршрутизацией, retries и ошибочными сообщениями. |
| NATS JetStream | Persistent streams, subjects, независимые consumers, replay, настраиваемые storage/retention; at-least-once и повтор при отсутствии ack. Обычный Core NATS — at-most-once, без replay. [JetStream](https://docs.nats.io/concepts/jetstream) | Сильная альтернатива RabbitMQ, особенно для истории событий/replay. Выбирать именно JetStream и file storage; потребуется освоить stream/consumer и срок хранения. |
| Redis Streams | Consumer groups, pending entries, `XACK`; `XAUTOCLAIM` передаёт зависшие сообщения другому consumer. Запись на диск зависит от RDB/AOF. [XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/), [XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/), [persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) | Разумно при уже необходимом Redis. Сейчас не уменьшает число продуктов: появятся свои правила retention, восстановления pending и persistence. |
| Kafka | Разделённый на partitions журнал, offsets потребителей, повторное чтение; транзакционные гарантии имеют определённую область действия. [Kafka: design](https://kafka.apache.org/41/design/design/) | Рассмотреть, если цель — изучить event streaming, partitions и replay. Для одного фонового сценария на неделе понятий больше, чем нужно; это оценка сложности, не утверждение о непосильной RAM. |

Redis Streams нельзя оценивать как «Redis кеш, значит сообщения переживут всё»: AOF `everysec` допускает потерю примерно секунды записей при аварии, RDB имеет другую цену потери данных. [Redis: persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
Kafka запускается локально по официальному quickstart; неверно утверждать, что он требует большого production-кластера просто для знакомства. Но возможность запуска не равна полезности именно для этого срока. [Kafka: quickstart](https://kafka.apache.org/41/getting-started/quickstart/)
Shortlist брокера: RabbitMQ и NATS JetStream; взять **один**, после выбора асинхронного сценария. HTTP оставить для запросов, где ответ нужен сразу.

## Что означают подтверждения и повторы

1. **Publisher confirm**: брокер подтверждает публикацию; это не свидетельство завершения работы получателем. **Consumer ack**: получатель подтверждает брокеру обработку; механизмы независимы. [RabbitMQ: confirms](https://www.rabbitmq.com/docs/confirms)
2. Подтверждать обработку предлагается после успешной транзакции получателя. Если процесс умрёт после commit и до ack, повтор доставки возможен; потерянный confirm также может привести к повторной публикации. [RabbitMQ: reliability](https://www.rabbitmq.com/docs/reliability)
3. **Идемпотентность** — повторное событие не создаёт второй бизнес-эффект. Практический кандидат: `event_id`, таблица обработанных событий с UNIQUE и изменение бизнес-данных в одной локальной транзакции. [RabbitMQ: reliability](https://www.rabbitmq.com/docs/reliability), [PostgreSQL: constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [transactions](https://www.postgresql.org/docs/17/tutorial-transactions.html)
4. Не отправлять ошибочное сообщение в мгновенный бесконечный requeue: такие циклы расходуют CPU и сеть. Предложение: ограниченные попытки с задержкой, затем отдельная очередь ошибок и понятный лог. Dead lettering требует конфигурации. [RabbitMQ: confirms](https://www.rabbitmq.com/docs/confirms), [dead letter exchanges](https://www.rabbitmq.com/docs/dlx)
5. Для переживания перезапуска RabbitMQ нужны durable queue, persistent messages и корректные confirms; отдельно нужен постоянный volume. Это не защита от потери единственного диска. [RabbitMQ: queues](https://www.rabbitmq.com/docs/queues), [confirms](https://www.rabbitmq.com/docs/confirms), [Docker: volumes в Compose](https://docs.docker.com/compose/intro/compose-application-model/)

Не обещать «exactly once для всей системы». Даже Kafka отдельно оговаривает координацию при записи во внешнее хранилище; подтверждения одного транспорта не делают PostgreSQL и брокер общей транзакцией. [Kafka: delivery semantics](https://kafka.apache.org/41/design/design/), [AWS: transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

### Outbox — кандидат для одного важного сценария

Проблема: запись БД успешна, публикация события не удалась — следующий сервис не узнает об изменении. Обратный порядок тоже может дать несогласованность. [AWS: transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
Паттерн: в одной транзакции записать бизнес-изменение и строку outbox; отдельный отправитель публикует её и отмечает отправку. Дубликаты по-прежнему возможны, поэтому получателю нужна идемпотентность. [AWS: transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
Цена для недели — вывод: дополнительная таблица, периодический отправитель, повторные попытки, очистка старых записей, тест сбоя между публикацией и отметкой. Рассмотреть для одного главного события; не начинать с CDC-платформы и общей saga-инфраструктуры.

## Ресурсы и проверяемое качество

Из 31 GiB RAM нельзя вывести точное потребление шести ещё не написанных сервисов. Это зависит от языка, runtime, пулов соединений, размеров данных и очередей; в исследовании нет бенчмарков и обещаний вместимости.
Практическое предложение: сначала два сервиса + одна БД + один брокер, затем расширение до шести; смотреть фактическое потребление и размер накопленных сообщений. Один PostgreSQL вместо шести экземпляров сокращает число обслуживаемых процессов, но это не численная оценка экономии памяти.
У RabbitMQ memory watermark — порог включения alarm и блокировки publishers, а не жёсткий лимит RAM. Не приравнивать его к ограничению контейнера. [RabbitMQ: memory threshold](https://www.rabbitmq.com/docs/memory)
Предлагаемый минимум проверки: перезапуск с сохранением данных; недоступный получатель; повтор одного `event_id`; падение после commit до ack; ошибочное сообщение; запрет подключения к чужой БД. Это проверки обещаемого поведения, а не нагрузочный стенд.
Предлагаемый минимум диагностики: структурированные stdout-логи с service/request_id/event_id, понятные HTTP-ошибки без секретов и stack traces клиенту, отдельный лог неуспешной обработки сообщения. Полную платформу централизованного мониторинга не добавлять до появления потребности.
Auth не определяется выбором PostgreSQL/RabbitMQ: конкретные роли пользователя, владелец ресурса и правила межсервисного доступа нужно определить после предметной области. Не считать наличие JWT достаточной моделью разрешений.

## Итог исследования для обсуждения

- Наиболее цельный стартовый кандидат: **PostgreSQL — один экземпляр, отдельные БД/роли; RabbitMQ; HTTP/JSON REST; Docker Compose**.
- Равноправная развилка брокера: **NATS JetStream**, если ключевой сценарий лучше выражается сохраняемым потоком и replay.
- Если время уходит на инфраструктуру, допустимый облегчённый путь: отдельные SQLite-файлы; не менять одновременно базу, API и брокер.
- Redis cache, Kafka, gRPC и Kubernetes требуют отдельной причины; отсутствие их в прототипе не уменьшает само по себе его качество.
- Окончательно выбирать после предметной области и одного сквозного сценария: например, лаборатория/экспедиции/ремонтная мастерская с заявкой, назначением, результатом и уведомлением. Это идеи, не выбранная предметная область.

Ограничение исследования: документация проверена по прямым официальным страницам; измерений на этой машине, установки и запуска компонентов не было. Точные версии образов и поддерживаемую библиотеку выбранного языка следует закрепить перед реализацией.
