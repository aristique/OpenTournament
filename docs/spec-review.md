# OpenTournament: финальная сверка ТЗ 0.3

Статус: подготовлено к общему согласованию; это не автоматическое утверждение оставшихся предложений. Полное описание — [specification.md](specification.md), дизайн — [design-brief.md](design-brief.md), обучение — [learning-plan.md](learning-plan.md).

## Основные решения уже приняты

- CS2, Dota 2 и VALORANT; пять игроков, включая капитана, без запасных.
- Вместимость 4/8/16/32 команды; старт только при полном наборе, при недоборе продление или отмена до старта.
- Single и double elimination; в double условный повтор гранд-финала после победы нижней ветки.
- BO1/BO3/BO5: отдельно обычные встречи и финал; повтор наследует формат финала. Финалы верхней/нижней веток используют обычный формат.
- Случайный фиксируемый начальный посев; повтор запуска сохраняет пары.
- Любой зарегистрированный пользователь создаёт свои турниры. Организатор может участвовать; результаты утверждает организатор.
- Одна активная команда на игру; уже сыгранные зависимые встречи блокируют изменение прежнего результата.
- Сохраняемый вход после обновления страницы; уведомления внутри приложения.
- Шесть backend-сервисов, Python/FastAPI, PostgreSQL, RabbitMQ, REST, Docker Compose, один компьютер и собственный небольшой интерфейс.
- Поэтапная разработка с объяснением синтаксиса, самостоятельными заданиями и продолжением обучения после реализации.

## Конкретные оставшиеся предложения на общее согласование

| Область | Предложение | Последствие |
| --- | --- | --- |
| Команда | Приглашения существующим пользователям; капитан не покидает команду и не передаёт роль в первой версии; архивирование без активных заявок | Можно собрать и использовать команду; сложная смена руководства остаётся расширением |
| Состав на турнир | Снимок принятого состава неизменяем; текущая команда может меняться для будущих соревнований | Старые участники/уведомления не переписываются задним числом |
| Отмена и результаты | Отмена только до запуска; техническая победа вручную с причиной; завершённый турнир не переоткрывается | Нельзя автоматически переписать уже состоявшееся соревнование; это явное ограничение прототипа |
| Администрирование | Нет отдельного глобального администратора, независимых судей и процедуры спора | Первая версия доверяет организатору и проверяет владельца ресурса |
| Сохраняемый вход | Серверная сессия в identity, HttpOnly cookie, CSRF, начальный абсолютный срок 8 часов; серверный отзыв при выходе | Refresh сохраняет вход; защищённые запросы зависят от доступности identity, новый сервис не появляется |
| Frontend | Собственные HTML/CSS и модульный JavaScript, общая точка входа с API; структура страницы турнира по Challengermode, компактная навигация CYBERSHOKE, подача встреч BLAST | Меньше одновременно изучаемых инструментов; детальные макеты и удобство сетки проверяются отдельно до полной реализации UI |
| Надёжность | Отдельные БД/роли, воспроизводимые миграции, outbox, защита от повторных событий, восстановление незавершённого запуска | Нужны проверки сбоев и дубликатов, а не только успешный показ |

У сессии cookie без Max-Age/Expires: сохранение после закрытия браузера не обещается; абсолютный срок всё равно проверяется сервером. Выход отзывает дальнейшие проверки, но не откатывает уже авторизованный запрос или принятую фоновую работу. Детали — [ADR-0005](adr/0005-server-sessions.md).

## Что происходит после согласования

Сделать ТЗ 1.0 согласованной базой и принять предложенный ADR сессий. Затем проверить точные версии и работу выбранного окружения, пройти маленький учебный запрос и начать ограниченные этапы приложения. Собственный макет каталога/турнира проверяется на сценарии капитана и сетке 32 команд перед полной реализацией интерфейса. Подтверждение функционального объёма не означает одобрение ещё не показанных пиксельных деталей дизайна.

За неделю приоритет — согласованный качественный рабочий прототип, важные тесты и объяснимый сквозной сценарий. Срок не доказывает заранее готовность всех возможностей; трудности и изменение объёма обсуждаются явно, требования не исключаются молча.
