# Согласованный объём и открытые решения

## Подтверждено пользователем

- Предметная область: любительские турниры (ответ 2026-11-13).
- Шесть бизнес-микросервисов и локальный запуск на одном компьютере.
- Оптимизация означает баланс расхода ресурсов, скорости и понятности кода, а не максимизацию одной метрики.
- Нужна небольшая собственная пользовательская страница; интерактивная документация API остаётся полезной частью backend, но не заменяет этот интерфейс.
- До сдачи неделя, несколько часов работы в день; цель — качественное приложение, при ограничении срока допускается качественный рабочий прототип с дальнейшим расширением.
- Пользователь хочет самостоятельно разобраться и защитить проект; выдача непонятного готового проекта не отвечает цели.
- Название: OpenTournament; публичный репозиторий https://github.com/aristique/OpenTournament создан по запросу пользователя.
- Игры: Counter-Strike 2, Dota 2 и VALORANT.
- Вместимость турнира: 4, 8, 16 или 32 команды.
- Форматы: выбывание после одного поражения и верхняя/нижняя сетки с условным повтором гранд-финала.
- Порядок: сначала полное ТЗ и согласование, затем поэтапная реализация и обучение с разбором синтаксиса; после завершения кода обучение продолжается.
- Заявочный состав ровно пять игроков, включая капитана; без запасных.
- Серии BO1/BO3/BO5; отдельный формат обычных встреч и финала. Возможный повтор гранд-финала наследует формат финала.
- Старт только с полным выбранным числом команд; при недоборе продлить регистрацию либо отменить.
- Любой зарегистрированный пользователь создаёт собственный турнир и управляет только им.
- Backend-стек: Python/FastAPI, PostgreSQL, RabbitMQ, REST, Docker Compose.
- Для frontend требуется изучить реальные киберспортивные сайты, выбрать основу с упором на UX и доработать под OpenTournament; типовой автоматически сгенерированный интерфейс пользователь отверг.

## Пока предложено, но не принято

- Дополнительные правила членства, приглашений и изменения состава.
- Технические победы и ограничения исправления результатов.
- Случайный фиксируемый посев.
- Шесть сервисов: учётные записи и доступ; турниры; команды; заявки на участие; матчи и результаты; уведомления.
- Конкретная композиция frontend, технология страницы и Gateway; изучены семь платформ и визуально просмотрены рабочие страницы, предложено направление в design-brief.md.
- Срок и сохранение входа, дополнительные ограничения ролей и уведомления.

## Следующие вопросы

Полный проект ТЗ — specification.md 0.2, план обучения — learning-plan.md. Остаток P1–P7 обсуждать небольшими группами; принятые решения не спрашивать повторно. Поддержка выбранных версий и запуск — задача технической проверки, а не вопрос о предпочтениях пользователя.
