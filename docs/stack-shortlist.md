# Выбор стека: выводы для обсуждения

Дата: 2026-11-13. Статус: сравнение вариантов и последующий выбор backend; frontend остаётся открытым.

Обновление: после сравнения пользователь принял backend Python/FastAPI + PostgreSQL + RabbitMQ + REST + Docker Compose. Сравнение ниже сохраняет альтернативы и причины; визуальное направление frontend исследуется отдельно.

Подробные факты и первичные источники: [backend](backend-stack-research.md) и [инфраструктура](infrastructure-stack-research.md). Все оценки удобства относятся к новичку с недельным сроком и отсутствием подтверждённого опыта конкретного языка.

## Что означает актуальность

Поддерживаемая версия, совместимые зависимости, доступная документация и возможность воспроизвести сборку. Новизна релиза сама по себе не определяет качество выбора. Установленный .NET 8 уже завершил поддержку; при выборе C# исходный кандидат — .NET 10 LTS, с проверкой фактической сборки. Источники lifecycle — в исследовании backend.

## Что означает оптимизация — подтверждено пользователем

Баланс ресурсов, времени ответа и понятности реализации. Пользователь подтвердил этот смысл в раунде 2. Не выбирать язык по выдуманным RPS или расходу памяти пустого приложения. После выбора измерить время готовности, расход памяти сервисов и время ответа в основном сценарии, затем исправлять выявленные проблемы. Несколько языков и ORM одновременно не нужны для демонстрации независимости сервисов.

## Три главных кандидата без прежнего опыта языка

1. Python + FastAPI — основной кандидат при приоритете понятного, быстро проверяемого API и ограниченном времени. Автоматическая документация и валидация уменьшают вспомогательную работу; качество структуры, ошибок, доступа и данных всё равно нужно спроектировать.
2. C# + ASP.NET Core 10 LTS — сильная альтернатива для явных типов и цельной платформы. Потребует разобраться с C#, зависимостями и сборкой; OpenAPI UI настраивается отдельно. Наличие SDK 8 не подтверждает готовность сборки проекта на 10.
3. Go + net/http/chi — кандидат при желании явно изучать HTTP/SQL и при повышенном внимании к ресурсам. Конкретное преимущество по памяти не измерено; потребуется больше самостоятельной сборки проверки данных, документации и доступа.

TypeScript/NestJS/Fastify, Java/Kotlin/Spring, Django/DRF, Rust/Axum, Laravel и Rails не объявляются устаревшими или непригодными. Прежний опыт пользователя может изменить короткий список; подробное сравнение есть в исследовании.

## Инфраструктурный кандидат

REST/JSON + один PostgreSQL с шестью отдельными БД/ролями + RabbitMQ + Docker Compose. Отдельные БД и один сервер нужно отличать от единой общей бизнес-БД; разрешения подключения/чтения проверить тестом. NATS JetStream — альтернатива после выбора сценария событий; SQLite — облегчённая альтернатива хранения. Kafka, Redis, gRPC и Kubernetes могут быть полезны при конкретной потребности, но не должны добавляться автоматически ради «современности».

RabbitMQ сам по себе не устраняет потерю события между записью БД и публикацией и не запрещает повтор обработки. После выбора сценария нужно согласовать требуемую надёжность; для одного важного события рассмотреть outbox и защиту от дубликатов. Это не принятое обязательство внедрить универсальную платформу обработки событий.

## Важное ограничение доказательств

Проверено на машине: Python HTTP loopback, SQLite в памяти, запуск тестового Linux-контейнера. Не проверено: выбранные версии библиотек, PostgreSQL/RabbitMQ, шесть бизнес-сервисов вместе и показатели производительности. Готовность полного стека подтверждается отдельно после выбора, до основной реализации.

## Ответы раунда 2

- Тема: любительские турниры.
- Приоритет оптимизации: баланс скорости, памяти и понятности.
- Демонстрация: нужна собственная небольшая пользовательская страница.

В последующем ответе backend-стек принят; конкретные версии/библиотеки требуют проверки. Frontend не был автоматически принят вместе с backend.
